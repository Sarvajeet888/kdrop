What this is

K-Drop is a web page that moves files between two devices. You open it on both, match a six-character code, and the transfer runs over a direct browser-to-browser connection. On a shared Wi-Fi network the bytes never leave the building.

It exists because the obvious alternatives all have a cost. Emailing a file to yourself caps out at 25 MB. Cloud drives upload the whole thing to a datacentre and back down again, which is slow and leaves a copy behind. Cable transfers need the right cable and the right drivers. Installed transfer apps have historically paid for themselves with advertising and background data collection.

K-Drop does the one job and stops there. No feed, no rewards, no notifications, no installer.

The short version

Two browsers, one code, one direct connection. The server introduces the devices and then gets out of the way.

Why it is called what it is

A Kalman filter takes a noisy measurement and produces a converged estimate — signal recovered from noise. That is where the company name comes from, and it is why the connection indicator on the front page is a noisy line resolving into a clean one rather than a spinner. Iron is the raw measurement. Vermillion is the resolved state. The same rule holds in every chart and interface we build.

K-Drop applies the same idea to a dull problem: remove everything that is not the file, and move what is left.

How to use it

  1. Open the site on the sending device. A six-character code and a four-character PIN appear under step 01.
  2. Open the same site on the receiving device — scan the QR code, or type the code and then the PIN into the join box. Both are required — the PIN is what encrypts your files if the network forces the slower route, so K-Drop will not let you pair without it.
  3. The second device appears in the device list, and the trace under step 01 settles. It will read Direct or Relayed.
  4. Drag files onto the drop zone, choose a folder, or paste an image straight onto the page.
  5. The receiving device is asked to accept. Once it does, the transfer starts.

Trusted devices

After a transfer works, K-Drop offers to remember the other device. Accept, and next time it will not ask you to approve each transfer from that device.

This is bound to a secret, not a name. On the first pairing the two devices agree a random value that neither we nor anyone else ever sees. To be recognised later, a device has to prove it holds that secret by answering a fresh challenge — so a device that merely calls itself by a familiar name is treated as a stranger.

The list lives in your browser, never on our server. You can turn off automatic accepting for any device, or forget it entirely, from the trusted devices panel.

Seeing what you are sending

Pick some files and K-Drop shows small previews of them. Photos get a real thumbnail; everything else gets a mark for its type. These are made on your own device from the file you already have, and are never sent anywhere — they exist to catch the mistake people actually make, which is picking the wrong photo.

When a transfer finishes you get a summary: how many files, how large, how long it took, the speed, and which route it used.

Leaving the app mid-transfer

If you switch to another app and come back, K-Drop picks the transfer up where it stopped. The phone will usually have frozen the page and dropped the connection while you were away; returning asks the other device what it actually received and continues from exactly there.

Closing the tab is different, and it stops the transfer. When a browser tab closes, the page and everything in it stop existing — the connection, the file, the keys. No website can survive that, which is why transfers keep running in apps like AirDrop but not here. K-Drop asks your phone to keep the screen on while a transfer is running, which prevents the most common accidental version of this.

A true background transfer would need a native Android app running a foreground service. That is a different piece of software, and it is on the list rather than in the product.

Sending or receiving

The two buttons at the top decide what the page shows you. Choosing Receive puts the code box first and takes the file controls away, because a receiver has nothing to choose. Choosing Send does the opposite. Either device can do either job, and you can switch at any point — the buttons only change what is in front of you.

If something is not available

K-Drop checks what your browser and connection can actually do and says so at the top of the page rather than failing quietly. The common one: opening the site over a plain http:// address on a local network means the browser will not provide the encryption the fallback route uses, and will not let a page save straight to a folder. Transfers still work and are still encrypted by the browser itself. A deployed site over https has everything switched on.

On a phone

K-Drop follows your system's light or dark setting. If your browser supports it, you can scan the other device's QR code from inside the page rather than leaving for the camera app — where it does not, typing the code and PIN works exactly as well.

While a transfer is running, K-Drop asks the phone to keep the screen awake, because a sleeping phone stops the transfer. That request is dropped the moment nothing is moving. If you leave the app mid-transfer you will be warned, and the transfer will stop — there is no background mode, and pretending otherwise would just lose your file quietly.

The Text tab

For a link, an address, or a Wi-Fi password you would otherwise retype by hand. It arrives on the other device with a copy button.

Where received files land

On Chrome and Edge, K-Drop asks once for a folder and then streams each file straight to disk, so a file larger than the device's memory still works. Everywhere else, files are held in memory and a save link appears when the transfer completes.

Languages

K-Drop is available in English and Hindi. More languages can be added — the site is built so that translating one file adds a language to the menu, and right-to-left layouts already work.

We have not added more yet, and that is deliberate. These pages make specific claims about what happens to your files, and a translation of a privacy claim should come from someone who speaks the language rather than from a guess. If you speak a language we do not cover and want to help, the strings live in one file in the source.

Transfer history

K-Drop remembers what you sent and received, in a list under the transfer panel. That list is stored in your own browser and never sent to us. We have no account to attach it to and no reason to know what you moved.

It keeps filenames, because that is the only thing that makes the list useful — which is exactly why it stays on your device. Clearing it is one button, and using a private window leaves nothing behind at all.

Run your own copy

K-Drop is small enough to read in an afternoon — one server file and four client files, three dependencies, no build step. If you would rather host it yourself, everything you need is in the README that ships with the source: how to run it, how to deploy it, and every configuration option.

You do not need to do any of that to use K-Drop. This is here for people who want to check what the code actually does, or run it on their own network.

How it works

Pairing

One device asks our server for a code. The code leaves out characters that look alike, so nobody misreads a zero as an O across a room. The PIN beside it is made on your own device and is never sent to us. It travels only inside the QR link, in the part of a web address that browsers keep to themselves — which is what lets us forward encrypted data on the slower route without being able to read it.

Connecting

Our server passes a few short messages between the two browsers so they can find each other. Once they have, they open a connection directly between themselves and the server stops being involved. It never sees the file.

Some networks — a lot of college and office Wi-Fi — block browsers from connecting to each other directly. If that has not worked after about nine seconds, K-Drop falls back to passing the file through our server instead, and tells you on screen that it has. That route is slower, and everything on it is encrypted before it leaves your device.

Moving the file

The file is sent in small pieces rather than all at once, and the sender keeps an eye on how much is still waiting to go out. Without that, a large file would pile up faster than the network could clear it and the tab would run out of memory.

Every file is fingerprinted as it leaves and again as it arrives. If a single byte is wrong, you are told — rather than quietly handed a file that looks fine and is not.

Getting the most speed

Speed is set almost entirely by the path between your two devices, not by K-Drop. The round-trip time shown next to the connection is the number that predicts it.

Round tripWhat it means
Under 20msSame Wi-Fi. The fast case — expect tens of megabytes a second.
20–80msNearby, but not the same network. Noticeably slower.
Over 80msA long route, often one device on mobile data. Speed drops sharply, because every acknowledgement has to make that trip.

Seeing the actual numbers

Open Connection details under step 01 while two devices are connected. It shows the real round-trip time, which network path was chosen, the frame size, and whether the receiving browser can write to disk.

The path is the useful one. host/host means the two devices found each other on the same network — the fast case. Anything mentioning relay means the traffic is detouring, and the panel says what would fix it.

There is a button to copy all of it as text for a bug report. It deliberately leaves out your session code and PIN, since those are the keys to the session.

Three things that actually help

  1. Put both devices on the same Wi-Fi. This matters more than everything else combined, often by twenty times or more.
  2. Choose a folder when asked. On Chrome and Edge this writes the file to disk as it arrives instead of holding it in memory, which keeps large transfers fast all the way through.
  3. Keep the screen on during a phone transfer.

What is possible at all

Wi-Fi hardware tops out around 100 MB/s and a gigabit cable around 125 MB/s. Those are the real ceilings — no software can move bytes faster than the wire carries them. On a good local network, tens of megabytes a second is what a working transfer looks like.

A relayed connection is slower than a direct one by definition, since the data detours through our server and is encrypted on the way.

Limits

Stated plainly, because a product page that hides these is not worth trusting.

  • Both devices must stay open. There is no mailbox. Close the tab and the transfer stops.
  • One transfer moves at a time. You can queue more while one is running; they go one after another rather than at once.
  • Two devices at a time on the slower route. If your network forces the relayed route, keep it to one pair of devices. The direct route handles more.
  • A dropped connection resumes, but the tab must stay open. If Wi-Fi drops mid-transfer, K-Drop reconnects and continues from where it got to. Reloading the page or closing the tab loses the partial file.
  • Very large files need Chrome or Edge. Those browsers write the file to your disk as it arrives, so size is not really a limit. Safari and Firefox have to hold it in memory first, so a very large file can fail there.
  • Not a backup tool. Nothing is retained. That is the design, not a missing feature.
