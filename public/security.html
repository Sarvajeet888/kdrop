Security

What protects your files, what does not, and how to tell us if you find a hole.

The model in one paragraph

Two browsers pair with a six-character code and a four-character PIN. The code identifies a session on our server; the PIN never reaches us. The browsers then connect directly and move the file between themselves. If the network blocks a direct connection, the file is encrypted on your own device with a key derived from the PIN and passed through our relay as data we cannot read. Nothing is written to disk on our side.

What protects each path

PathProtection
DirectDTLS, applied by the browser. Mandatory in WebRTC and not something we can switch off.
RelayedAES-256-GCM per chunk, under a key agreed fresh for each session by ECDH on P-256. The private halves never leave the device and are discarded when the tab closes.
PairingTLS between your browser and our server.
IntegrityA CRC-32 over every file, checked on arrival. A mismatch is reported rather than saved.

The code you can check yourself

When two devices connect, both display a twelve-character code worked out from the encryption keys they agreed. If the codes on the two screens match, nothing interfered with the exchange.

Every other check here is done by software. This is the one a person performs, and it is the only one that can catch interference the software cannot reason about. It is offered rather than forced — most transfers do not warrant it, and a prompt nobody reads protects nobody.

The code uses the same alphabet as the pairing code, with characters that look alike removed, because it gets read aloud across a room.

Forward secrecy

The key that encrypts a relayed transfer is agreed by the two devices at the moment they connect, from throwaway keypairs that exist only for that session. Nothing that could reconstruct it is written down anywhere.

This means a recording of today's relayed session cannot be decrypted tomorrow — not by us, not by whoever made the recording, and not by someone who later learns your code and PIN. Earlier versions derived the key from the code and PIN alone, which made the same code produce the same key every time; that is no longer the case.

The PIN still does essential work. Our own server relays the public keys during the exchange, so without authentication a malicious relay could substitute its own and read everything. Each public key is therefore sent with a fingerprint computed under the PIN, and a key that does not verify is refused rather than trusted.

Why the PIN is not optional

The PIN is the only input to the relay key that we never see. It travels in the fragment of the pairing link — the part after the #, which browsers do not send to servers — or you type it by hand.

Joining with only the code would still connect, and would silently lose that protection the moment a network forced the relayed route. A quiet downgrade is worse than a refusal, so K-Drop refuses: pairing without a PIN is rejected in the interface and again in the transport underneath it.

What this does not protect against

Stated plainly, because a security page that only lists strengths is marketing.

  • Someone who can see your screen. The code and PIN are shown in plain sight. Anyone who reads them within the session's lifetime can join it.
  • A compromised device. If malware is running on either end, encryption in transit does not help. It reads the file before we ever touch it.
  • Accepting from a stranger. You are shown what is being sent and by which device, and nothing moves until you accept. That check is yours to make.
  • Traffic analysis on the relay. We cannot read relayed content, but we can see that a session exists, roughly how much data moved, and when. We do not keep that beyond the session.
  • A malicious server operator. If someone ran a modified copy of this code, they could serve you altered JavaScript. That is true of every web application, and it is why the source is open — you can read exactly what this one does, or run your own copy.

Filenames

A filename arrives from the other device, so it is treated as untrusted input even in a session you started deliberately.

Before anything is written to disk, paths are stripped, control characters and null bytes are removed, Windows reserved names are escaped, and over-long names are trimmed with the extension kept.

The one worth explaining: Unicode contains characters that reverse text direction. A file named invoice‮gnp.exe is displayed by almost every operating system as invoiceexe.png — you see a picture and save a program. Those characters are removed, so the name you are shown is the name that gets saved.

If a name had to be changed, or if the file runs when opened, the accept dialog says so. Nothing is blocked — people send installers for good reasons — but the decision is yours to make with the truth in front of you.

Hardening on the server

  • Content Security Policy, frame denial, MIME-sniffing off, referrer suppressed, HSTS over HTTPS.
  • Rate limits per address on sessions and connections, with a temporary cool-off after repeated abuse.
  • A ceiling on relayed bytes per session.
  • Oversized and malformed control messages rejected before parsing; burst detection on the socket.
  • Repeated wrong session codes treated as guessing and cooled off. Six characters from a 31-character alphabet is roughly 887 million combinations, so guessing is impractical to begin with.
  • Sessions expire after 30 minutes idle, and no connection is held beyond six hours.
  • Operational metrics are not public.

Reporting a vulnerability

If you find something, please tell us before telling anyone else. We would much rather hear it from you.

Contact: security reports go to the Kalman founders. Replace this line with a monitored address before sharing the site publicly — the release gate refuses to pass until you do.

Useful things to include: what you did, what happened, what you expected, and how serious you think it is. A rough proof of concept helps more than a scanner report.

What we ask

  • Give us a reasonable chance to fix it before publishing.
  • Test against your own sessions and your own files, not other people's.
  • No denial-of-service testing against the live service — tell us instead, or run your own copy and test that.

What you can expect

  • An acknowledgement that a person has read it.
  • An honest assessment, including if we disagree that it is a problem.
  • Credit when it is fixed, if you want it.

K-Drop is run by two people and is free. We cannot offer a bounty. We can offer a straight answer and a fix.

Honest status

Transfers are verified byte-for-byte by automated tests on both the direct and the relayed route, including recovery after a dropped connection. Fourteen automated suites cover abuse handling, hostile input, filename safety, injection, accessibility and load. A full third-party security audit has not been done. The service is in public beta and labelled as such.

The operator details are in the privacy section of the documentation.
